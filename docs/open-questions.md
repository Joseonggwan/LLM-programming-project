# 초기 개발 환경 결정 기록

사용자가 선택한 항목을 기록한다. 제안서에서 이미 정한 프로젝트 범위나 역할 분담은 다시 묻지 않는다. 답변 `ABAAA`는 아래 순서대로 1A, 2B, 3A, 4A, 5A로 해석했다.

## 1. 첫 실행 환경 — 결정: A

- **A. 로컬 Python 가상환경 (추천)** — 장점: 반복 실행과 파일 관리가 간단하고 의존성 범위를 통제하기 쉽다. 단점: OS별 설정 차이를 확인해야 한다.
- **B. Google Colab** — 장점: 초기 설정과 GPU 접근이 편리할 수 있다. 단점: 세션·파일 경로가 바뀌고 재현 절차가 노트북 중심이 되기 쉽다.
- **C. 둘 다 지원** — 장점: 유연하다. 단점: 초기부터 경로·의존성 차이를 관리해야 한다.

**추천 이유:** 우선 로컬에서 작고 재현 가능한 정적 하네스를 시작하면 시스템 요구를 낮게 유지할 수 있고, 필요해질 때 Colab을 추가하기 쉽다.

## 2. Python 기준 버전 — 결정: B

제안서는 **Python 3.10 이상**을 요구하지만 상한/정확한 버전은 정하지 않았다.

- **A. Python 3.10으로 고정 (추천)** — 장점: 제안서 최소 버전과 일치하고 호환성 기준이 명확하다. 단점: 이후 최신 라이브러리가 더 높은 버전을 요구할 수 있다.
- **B. 사용 가능한 최신 안정 버전으로 고정** — 장점: 새 기능과 최신 런타임을 쓸 수 있다. 단점: 일부 시뮬레이터/라이브러리 호환 여부를 초기에 확인해야 한다.
- **C. 버전 범위만 정하고 잠금 파일은 나중에 생성** — 장점: 선택 폭이 넓다. 단점: 실행 환경에 따라 재현성이 낮아질 수 있다.

**결정:** Python 3.15.2. 초기 단계는 구조화 시나리오와 API 호출 중심이며, CARLA/이미지 인식 라이브러리는 포함하지 않는다. 해당 항목을 추가할 때는 호환성을 다시 확인한다.

## 3. 첫 지도/경로 어댑터 — 결정: A

제안서는 OSRM 또는 사용 가능한 지도 API를 후보로 들며, 특정 공급자를 확정하지 않았다.

- **A. OSRM 어댑터 + 저장된 응답 fixture (추천)** — 장점: 노트북에서 이미 OSRM 실험 흔적이 있고, fixture로 외부 네트워크 없이 재현할 수 있다. 단점: 공개 서비스의 가용성/제공 정보에 의존할 수 있어 실시간 호출을 평가 기준으로 삼기 어렵다.
- **B. 다른 지도 API를 먼저 선택** — 장점: 원하는 지역/도로 정보를 더 잘 제공할 수 있다. 단점: API 키, 사용 조건, 접근 설정이 필요할 수 있다.
- **C. 우선 fixture 전용 인터페이스** — 장점: 네트워크와 계정 없이 하네스·평가 형식을 정할 수 있다. 단점: 실제 지도 도구 연동을 후속 작업으로 미룬다.

**추천 이유:** 공급자 중립 인터페이스와 저장 응답으로 시작하면 도구 결과만 사용한다는 설계 원칙을 유지하면서도 재현성을 확보할 수 있다. OSRM을 최종 공급자로 채택할지는 별도 선택이다.

## 4. 초기 환경 입력 범위 — 결정: A

- **A. 구조화된 시나리오 입력만 사용 (추천)** — 장점: CV 모델/가중치 없이 안전 규칙과 경로 비교를 먼저 검토할 수 있다. 단점: 이미지 인식은 평가하지 않는다.
- **B. 이미지 입력과 객체 탐지를 초기부터 포함** — 장점: 제안서의 CV 경로를 일찍 살펴볼 수 있다. 단점: 모델·데이터·연산 자원 및 오탐 평가까지 초기 설정이 늘어난다.
- **C. 구조화 입력부터 시작하고 입력 어댑터만 확장 가능하게 설계** — 장점: 단계적으로 CV를 더할 수 있다. 단점: 입력 스키마에 약간의 선행 설계가 필요하다.

**추천 이유:** 규칙 모듈과 후보 비교의 동작을 인식 모델 변수와 분리해 확인할 수 있는 구조화 입력부터가 초기 하네스에 적합하다.

## 5. 첫 평가 하네스 — 결정: A

제안서는 CARLA **또는** 재현 가능한 정적 시나리오를 허용하므로 선택이 열려 있다.

- **A. 정적 시나리오 우선 (추천)** — 장점: 설치 부담이 낮고 입력·기대 판정·반복 실행을 빠르게 고정할 수 있다. 단점: 동적 상호작용과 시뮬레이터 통합을 다루지 못한다.
- **B. CARLA 우선** — 장점: 동적 주행 장면과 시뮬레이션 연계를 평가할 수 있다. 단점: 설치·실행 환경과 시나리오 작성 부담이 더 크다.
- **C. 정적 하네스 후 CARLA 추가** — 장점: 기본 규칙 검증과 시뮬레이터 평가를 단계적으로 진행할 수 있다. 단점: 두 평가 경로를 관리해야 한다.

**추천 이유:** 초기 개발 하네스의 재현성과 빠른 반복을 먼저 확보한 뒤 CARLA 필요성과 실행 여건을 확인하는 순서가 위험이 낮다.

## JSON 시나리오 스키마 초안 결정

시나리오 레코드는 다음 구조를 기준으로 작성한다. 좌표 필드는 초기 정적 fixture 범위에서 제외하고, 출발지와 목적지는 장소 설명(label)으로 기록한다. 경로 후보의 거리와 시간은 도구 응답값을 사용한다.

```json
{
  "schema_version": "1.0",
  "scenario_id": "intersection_pedestrian_001",
  "description": "보행자가 있는 교차로 접근 상황",
  "origin": { "label": "출발지 설명" },
  "destination": { "label": "목적지 설명" },
  "route_data": {
    "provider": "OSRM",
    "fixture_id": "fixture_001",
    "routes": [
      {
        "route_id": "route_1",
        "distance_m": 1250,
        "duration_s": 210,
        "steps": [
          { "maneuver": "turn-right", "road_name": null, "distance_m": 300 }
        ]
      }
    ]
  },
  "environment": {
    "traffic_signals": [ { "state": "red", "distance_m": 15 } ],
    "pedestrians": [ { "state": "present", "distance_m": 8 } ],
    "vehicles": [],
    "lane_change_available": "unknown",
    "other_hazards": []
  },
  "expected": {
    "safety_decision": "review",
    "expected_route_id": null,
    "reason": "신호와 보행자 상황을 확인해야 함"
  }
}
```

### 필드 및 검증 규칙

- 필수 최상위 필드: `schema_version`, `scenario_id`, `description`, `origin`, `destination`, `route_data`, `environment`, `expected`.
- `distance_m`는 미터, `duration_s`는 초 단위의 음수가 아닌 숫자로 기록한다. 값은 경로 도구 응답에 근거해야 한다.
- `route_id`는 한 시나리오의 후보 안에서 고유해야 한다. `expected_route_id`가 문자열이면 후보 ID 중 하나여야 한다.
- `safety_decision`은 `allow`, `block`, `review` 중 하나다. `block` 또는 `review`이면 `expected_route_id`는 `null`이어야 한다.
- 신호 `state`는 `red`, `yellow`, `green`, `unknown`; 보행자 `state`는 `present`, `absent`, `unknown`으로 제한한다. `lane_change_available`은 `true`, `false`, `unknown`을 허용한다.
- `null`은 해당 필드의 값이 제공되지 않았음을 뜻하고, `unknown`은 항목은 평가 대상이지만 상태를 알 수 없음을 뜻한다. 빈 배열은 해당 항목이 관측되지 않았음을 뜻한다.
- 예시 값은 형식을 설명하기 위한 것이며, 실제 시나리오 데이터는 도구 fixture 및 명시된 입력 근거에 따라 작성한다.
- 위 구조를 초기 스키마 초안으로 채택했다. 정식 JSON Schema/Pydantic 검증 구현은 하네스 구현 단계에서 추가한다.


## 초기 평가 시나리오 10개 초안

아래 목록은 초기 정적 평가의 시나리오 구성 계획이다. 아직 시나리오 JSON이나 OSRM fixture 데이터를 생성한 것은 아니다. `allow`는 입력에서 안전 규칙 위반이 발견되지 않은 상태, `block`은 명시된 규칙과 충돌하는 계획/행동, `review`는 정보가 불확실해 추가 확인이 필요한 상태로 제안한다.

| # | 상황 | 기대 판정 | 평가 초점 |
|---|---|---|---|
| 1 | 녹색 신호, 보행자 없음 | `allow` | 기본 통과 및 필수 출력 |
| 2 | 교차로 적색 신호 | `block` | 신호 위반 계획 차단 |
| 3 | 교차로 황색 신호 | `review` | 신호 불확실 상황에서 승인 보류 |
| 4 | 보행자가 횡단보도를 건너는 중 | `block` | 보행자 충돌 위험 처리 |
| 5 | 보행자가 횡단보도 근처에 있으나 진행 상태 불명 | `review` | 미확인 정보를 확정 사실처럼 다루지 않는지 |
| 6 | 차선 변경이 필요하지만 변경 가능 여부가 `false` | `block` | 불가능한 기동 차단 |
| 7 | 차선 변경 가능 여부가 `true`, 인접 차선에 차량 없음 | `allow` | 조건을 만족하는 기동과 근거 설명 |
| 8 | 차선 변경 경로에 인접 차량 있음 | `block` | 위험한 차선 변경 차단 |
| 9 | 경로 후보는 있으나 신호 상태가 `unknown` | `review` | 알 수 없는 상태에서 승인 보류 |
| 10 | 안전 조건을 만족하는 경로 후보가 둘 이상 | `allow` | 선택 경로 ID가 도구 후보에 포함되는지 |

### 안전 규칙 경계 조건 결정

- **적색 신호:** 해당 신호를 통과하는 계획은 `block`한다.
- **횡단 중인 보행자:** 보행자와 충돌할 수 있는 경로 또는 행동은 `block`한다. 안전한 대체 후보가 없으면 승인하지 않는다.
- **신호/보행자 상태 미확인:** 상태가 `unknown`이거나 필수 상태 정보가 누락되면 `review`하고 승인 경로를 선택하지 않는다.
- **황색 신호:** 기본 판정은 `review`다. 현재 입력에는 정지 가능 거리나 제동 조건이 없어 안전 정지 여부를 판단할 근거가 부족하므로, 관련 정보가 추가되기 전까지 통과를 `allow`하지 않는다.
- **차선 변경:** `lane_change_available`이 `true`이고 인접 차선의 차량·보행자 위험이 없다고 입력에 명시된 경우에만 `allow`한다. 값이 `false`이거나 위험이 확인되면 `block`, 값이 `unknown`이거나 주변 정보가 누락되면 `review`한다.

이 규칙은 정적 시나리오 기반 프로토타입의 판정 기준이며 실제 차량 제어 기준은 아니다. 실제 거리, 시간, 도로 정보와 fixture ID는 OSRM fixture에서 가져오며 임의로 만들지 않는다. `expected_route_id`는 실제 fixture의 후보 ID로 채운다. 이 목록은 제안서의 최소 10개 시나리오 계획을 구체화한 초안이며, 구현·실행 완료를 뜻하지 않는다.


## OSRM fixture 지역 결정

초기 경로 fixture의 대상 지역은 **서울 도심 종로구·중구 경계 일대(광화문·종각·시청 주변)**로 정한다. 교차로와 보행자 상황을 다루는 정적 시나리오에 적합하고, 테스트 지역을 좁혀 입력을 관리하기 쉽다. 실제 OSRM 응답 fixture를 `data/fixtures/osrm_seoul_central.json`에 저장했다. 조회 시점, 요청 URL, 원본 응답과 좌표 출처를 함께 보존한다. 광화문광장→서울광장은 후보 1개(1,416.6m, 140.7s), 종각역→서울역은 후보 2개(2,399.7m/176.2s, 2,541.8m/188.1s)를 반환했다. 경로 비교 시나리오는 후보가 둘인 종각역→서울역 fixture를 사용한다. OSRM 응답과 소요 시간은 조회 시점 기준이며 이후 달라질 수 있다.


## OpenAI API 키 관리 결정

- 로컬 개발 키는 프로젝트 루트의 `.env` 파일에 `OPENAI_API_KEY`로 둔다.
- 앱은 `python-dotenv`로 `.env`를 읽는다. `python-dotenv`는 프로젝트 의존성에 포함한다.
- `.env`는 `.gitignore`에 추가해 버전 관리에 포함하지 않는다. 저장소에는 실제 키를 넣지 않는다.
- 실제 키 발급과 설정은 API 구현 단계에서 진행한다.


## OpenAI API 인터페이스 결정

초기 LLM 호출은 OpenAI Responses API를 사용한다. Python SDK의 `client.responses.create(...)`로 경로 후보와 안전 규칙 모듈 결과를 입력하고, 응답 텍스트를 계획 설명으로 사용한다. 실제 함수 호출/툴 사용은 필요한 경우 후속 구현에서 추가한다. SDK 버전과 나머지 요청 파라미터는 구현 단계에서 정한다. 오류 및 재시도 정책은 아래에서 결정했다.


## LLM 응답 형식 결정

OpenAI Responses API의 Structured Outputs를 사용하고, Python Pydantic 모델로 응답 스키마를 정의한다. 초기 모델 출력은 다음 항목을 포함한다.

- `recommended_route_id`: 추천 경로 ID 또는 `null`; 앱은 이 ID가 실제 도구 후보인지 검증한다.
- `route_comparison`: 후보 ID와 입력 근거에 기반한 비교 요약
- `segments`: 선택 경로의 구간/기동과 행동 설명
- `evidence_refs`: 경로·환경 입력의 근거 참조
- `risks`, `unknowns`: 위험과 미확인 정보 목록
- `safety_summary`: 안전 규칙 모듈 결과에 대한 자연어 요약

안전 판정(`allow`, `block`, `review`)은 모델이 결정하지 않는다. 애플리케이션이 별도 안전 규칙 모듈의 결과를 응답에 포함하고, `block` 또는 `review`일 때 경로 추천을 승인하지 않도록 처리한다. Pydantic 스키마 정의와 검증 코드는 하네스 구현 단계에서 작성한다.


## OpenAI API 오류 및 응답 실패 처리 결정

- 연결 오류, 시간 초과, 속도 제한(429), 서버 오류(5xx) 등 SDK가 재시도 대상으로 지원하는 오류는 OpenAI Python SDK의 기본 재시도 정책(최대 2회)에 맡긴다. 초기 하네스에서는 별도의 애플리케이션 재시도 루프를 추가하지 않는다.
- 인증 오류, 잘못된 요청, 지원되지 않는 스키마 등 재시도로 해결되지 않는 오류는 자동 재시도하지 않고 오류로 기록한다.
- 응답이 없거나 Structured Outputs 결과를 검증/파싱하지 못하면 부분 응답을 사용하지 않는다. 해당 실행은 모델 추천 실패로 처리하고 승인할 경로를 내지 않는다.
- 모델 호출 실패와 무관하게 결정론적 안전 규칙 모듈의 판정은 보존한다. 다만 모델 응답이 유효하지 않으면 그 결과만으로 경로를 승인하지 않는다.
- 요청 시간 제한은 요청당 30초로 정한다. SDK 기본 재시도가 끝나도 실패하면 모델 추천을 보류한다.
- 오류 로그에는 오류 종류와 메시지, HTTP 상태 코드(있는 경우), 재시도 횟수, 시나리오 ID를 기록한다. API 키와 요청 전문은 기록하지 않는다.
