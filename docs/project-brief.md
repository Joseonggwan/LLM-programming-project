# 프로젝트 브리프

## 목적과 범위

제안서의 프로젝트명은 **AI 기반 자율주행 경로 계획 및 주행 전략 설명 Agent**이다. 제한된 주행 상황에서 경로 후보를 비교하고 고수준 구간 전략과 판단 근거를 설명하는 시연용 프로토타입을 목표로 한다. 대규모 자율주행 모델이나 저수준 제어기를 만드는 것이 목표는 아니다.

실제 차량 제어는 프로젝트 범위에서 제외한다. 초기 평가는 CARLA 시뮬레이션 또는 재현 가능한 정적 시나리오를 이용한다.

## 제안서에서 확인한 사실

- 출발지·목적지·주행 조건을 입력받고, 경로 후보가 2개 이상이면 후보별 거리, 예상 시간, 주요 위험 및 복잡도 항목을 비교하는 것이 목표다.
- 후보 경로와 도로 정보는 지도/경로 도구(OSRM 또는 사용 가능한 지도 API)가 제공한다. LLM은 도로 연결 관계나 좌표를 임의로 생성하지 않는다.
- CV 탐지 결과 또는 구조화된 환경 정보를 사용할 수 있다. 환경 정보에는 차량, 보행자, 차선, 신호등, 교차로 등이 포함될 수 있다.
- 안전 제약 검사는 별도 안전 규칙 모듈이 담당한다. 제안서가 예로 든 제약은 신호, 보행자, 차선 변경 관련 사항이다.
- LLM/Agent의 역할은 도구 및 입력 정보를 바탕으로 후보를 비교하고, 고수준 주행 전략을 구성하며, 선택 계획과 근거를 자연어로 설명하는 것이다.
- 출력 목표에는 추천 경로 ID, 주요 구간, 거리와 예상 시간(도구가 제공하는 경우), 구간별 행동, 고려한 환경 정보, 위험요소, 선택 근거, 안전 검사 결과, 미제공 정보 표시가 포함된다.
- 초기 평가는 CARLA 또는 재현 가능한 정적 시나리오로 한다. 정상 및 위험 상황을 살피고, 경로 유효성, 안전 규칙 위반, 출력 완성도, 설명의 근거 일치 여부를 기록·분석하는 것이 제안된 평가 방향이다.
- 최소 10개 시나리오(교차로, 차선 변경, 보행자/차량 위험 상황 등)는 **계획 단계의 목표**다. 현재 확보·구현된 수량을 뜻하지 않는다.
- 정량 성능 기준은 베이스라인 실행 후 확정한다고 제안서에 적혀 있다. 그러므로 통과 임계치나 확정된 정량 기준은 현재 **미정**이다.
- 제안서가 기술한 개발 환경 후보/요건은 Python 3.10 이상, PyTorch, LangChain, Streamlit, OpenCV, (탐지 사용 시) Ultralytics YOLO, Pydantic, 지도/경로 API 클라이언트 및 (시뮬레이션 사용 시) CARLA Python API다. 이는 후보 및 조건으로 적힌 내용이며, 지금 모두 설치하거나 사용하기로 확정된 것은 아니다.
- 연산은 일반 개발용 CPU를 기준으로 Agent 및 경로 분석을 하고, 탐지/시뮬레이션은 여건에 따라 GPU 또는 Colab GPU를 활용하는 구상이다. 구체적인 GPU와 모델 버전은 실험 환경에 맞춰 기록하도록 되어 있다.

## 구현 제안 (제안서의 설계안, 확정된 구현 사실 아님)

1. 사용자 입력과 환경 입력을 수집한다. 환경 입력은 카메라 프레임의 탐지 결과 또는 미리 구조화된 정보로 시작할 수 있다.
2. 지도/경로 도구에서 경로 후보와 도로 정보를 가져오고, 이를 명시적 입력 자료로 Agent에 전달한다.
3. 후보별 거리·시간·도로 복잡도·환경 위험을 비교한다.
4. 별도 규칙 모듈이 안전 제약과 경로 유효성을 검사한다. 검증 실패 시 재계획하는 흐름도 제안서 다이어그램에 제시되어 있다.
5. LLM은 검증 결과 및 후보 근거에 기반해 고수준 계획과 설명을 만든다. 도구가 제공하지 않은 사실을 덧붙이지 않고 미확인 사항을 드러내는 방향이 적합하다.
6. CARLA 또는 고정 입력 기반 시나리오로 재현 가능한 평가를 수행하고, 결과를 분석한다.

## 초기 개발 환경 결정과 남은 미정 사항

사용자가 `docs/open-questions.md`에서 선택한 초기 방향은 다음과 같다. 이는 하네스 준비 방향에 대한 결정이며, 구현/설치 완료를 뜻하지 않는다.

- 실행 환경: 로컬 Python 가상환경
- Python 버전: 3.15.2로 고정. CARLA 또는 이미지 인식 라이브러리를 추가할 때 호환성을 다시 확인한다.
- 지도/경로 입력: OSRM 어댑터와 저장된 응답 fixture로 시작
- 환경 입력: 구조화된 시나리오만 사용
- 첫 평가: 재현 가능한 정적 시나리오
- 시나리오 파일 형식: JSON. 각 레코드는 `scenario_id`, 목적/설명, 출발·목적지, 경로 도구 출처와 경로 후보(거리·시간·도로 정보), 구조화 환경 상태, 기대 안전 판정 및 사유를 담도록 정했다.

아직 정하지 않은 사항은 다음과 같다.

- LLM SDK 버전 및 세부 요청 파라미터 (구현 단계에서 확정)
- JSON 스키마 검증 코드의 세부 구현 (하네스 구현 단계)
- 평가 지표의 수치 임계치 및 최종 통과 기준 (베이스라인 후 결정)
- 추후 CARLA 또는 이미지 인식 입력을 추가할지 여부

## 평가 지표 결정

사용자가 초기 평가에서 다음 네 항목을 측정하기로 선택했다. 아래 항목은 측정 계획이며, 정량 합격 임계치는 아직 정하지 않았다. 제안서에 따라 베이스라인 실행 후 정한다.

1. **안전 판정 일치율:** 안전 규칙 모듈의 판정이 각 시나리오에 기록된 기대 판정과 일치한 비율.
2. **근거성:** 설명의 주장과 수치가 지도/경로 도구 응답 및 구조화 환경 입력으로 뒷받침되는지 점검한다. 입력에 없는 도로 연결·좌표·환경 사실을 생성한 사례도 기록한다.
3. **필수 출력 완성도:** 시나리오 상태에 해당하는 필수 출력 항목이 빠짐없이 포함되었는지 점검한다.
4. **경로 후보 유효성:** 경로 선택이 허용되는 경우 선택된 ID가 지도/경로 도구가 제공한 후보에 포함되는지 점검한다. 안전 규칙이 차단 또는 검토 필요 판정을 내린 경우에는 승인 경로를 선택하지 않는지 함께 기록한다.

최소 10개 시나리오는 제안서의 계획 목표다. 이는 현재 보유한 시나리오 수나 위 지표들의 합격선을 의미하지 않는다.

## 입력 자료 해석 메모

`proposal.md`는 위 범위와 의도에 대한 기준 자료다. `LLM Project.ipynb`에는 OSRM 요청, fixture 경로, 거리/시간/기동 수 비교, 규칙 판정 예시, LLM 설명 및 설명 검사 코드가 섞여 있다. 이는 탐색·실험 흔적으로 읽었으며, 완성된 앱이나 현재 프로젝트 코드베이스, 확정된 패키지/아키텍처/평가 결과의 증거로 취급하지 않는다. 노트북에 나온 예시 시나리오 몇 건도 제안서의 최소 10개 시나리오 목표를 충족했다고 볼 수 없다.

## LLM 및 Agent 구성 결정

초기 하네스부터 OpenAI API의 GPT-6.1 Terra (`gpt-6.1-terra`)를 사용하고, Python에서 OpenAI SDK/API를 직접 호출하기로 했다. 초기 구현에서는 LangChain 등 Agent 프레임워크를 사용하지 않는다. 제공자/모델을 나중에 바꾸기 쉽도록 호출부를 별도 인터페이스로 분리한다. SDK 버전과 API 설정은 구현 시 정하며, 모델 요금과 사용 가능 여부는 호출 시점에 확인한다.

## 의존성 관리 결정

초기 환경은 `uv`로 관리한다. 프로젝트 의존성은 `pyproject.toml`에 선언하고, `uv.lock`을 버전 관리에 포함해 설치 버전을 재현한다. 로컬 가상환경은 프로젝트의 `.venv`를 사용한다. 실제 패키지 설치 및 설정 파일 생성은 구현 단계에서 진행한다.

## 시나리오 JSON 스키마 결정

초기 정적 fixture용 시나리오 JSON의 구조와 검증 규칙을 `open-questions.md`의 **JSON 시나리오 스키마 초안 결정** 절에 기록했다. 필수 필드, 미터/초 단위, 경로 ID 참조, 안전 판정 enum 및 미상 값 처리 규칙을 포함한다. 좌표는 초기 범위에서 제외하고, 정식 JSON Schema/Pydantic 검증은 하네스 구현 단계에서 추가한다.

## 초기 평가 시나리오 계획

제안서의 최소 10개 시나리오 계획을 구체화한 초안을 `open-questions.md`의 **초기 평가 시나리오 10개 초안** 절에 기록했다. 신호, 보행자, 차선 변경 위험 및 복수 경로 후보 상황을 포함한다. 적색 신호 통과와 보행자 충돌 가능 계획은 `block`, 신호/보행자 상태가 미확인되면 `review`하고 승인하지 않는다. 황색 신호는 정지 조건 정보가 없어 기본 `review`로 하며, 차선 변경은 가능 여부가 true이고 인접 차선 위험이 없다고 명시된 경우에만 `allow`한다. 세부 기준은 `open-questions.md`에 기록했다. 실제 경로 수치와 fixture ID는 OSRM 응답에서 가져오며, 이 결정 기록만으로 실제 시나리오 데이터가 작성되거나 실행된 것은 아니다.

## 초기 OSRM fixture 지역

초기 경로 fixture 지역은 서울 도심 종로구·중구 경계 일대(광화문·종각·시청 주변)로 정했다. 두 출발·도착 쌍의 좌표와 원본 OSRM 응답을 `data/fixtures/osrm_seoul_central.json`에 저장했다. 광화문광장→서울광장은 경로 후보 1개, 종각역→서울역은 2개를 반환해 후자를 경로 비교 시나리오에 사용한다. 조회 시점과 출처도 fixture에 기록했다.

## OpenAI API 키 관리

로컬 개발에서는 `.env`에 `OPENAI_API_KEY`를 두고 `python-dotenv`로 읽는다. `.env`는 `.gitignore`에 포함하며 실제 키는 버전 관리에 올리지 않는다. API 키 발급·설정은 구현 단계에서 진행한다.

## OpenAI API 호출 인터페이스

초기 텍스트 생성은 OpenAI Responses API로 구현한다. Python SDK에서 경로 후보와 안전 검사 결과를 전달하고 결과 텍스트를 고수준 계획 설명에 사용한다. SDK 버전과 세부 요청 파라미터는 구현 단계에서 정한다. 오류 및 재시도 정책은 아래와 같이 결정했다.

## LLM 응답 형식

OpenAI Responses API의 Structured Outputs와 Pydantic 기반 스키마를 사용하기로 했다. 출력은 경로 ID 추천, 후보 비교, 구간별 행동, 근거 참조, 위험·미확인 정보 및 안전 요약을 구조화한다. 경로 ID 후보 검증과 안전 판정은 애플리케이션의 도구/규칙 모듈이 담당하며, 모델은 안전 판정을 독자적으로 결정하지 않는다.


## API 오류 및 응답 실패 처리

초기 하네스는 OpenAI Python SDK의 기본 재시도(지원되는 일시적 연결/시간 초과/429/서버 오류에 최대 2회)를 사용하며, 별도 애플리케이션 재시도 루프는 두지 않는다. 인증·요청·스키마 오류는 자동 재시도하지 않고 기록한다. 응답이 없거나 구조화 응답을 검증하지 못하면 부분 결과를 쓰지 않고 경로 추천을 승인하지 않는다. 이때도 결정론적 안전 규칙 모듈의 판정은 보존한다. 요청 시간 제한은 30초로 두고, SDK 재시도 후에도 실패하면 모델 추천을 보류한다. 오류 로그에는 오류 종류와 메시지, HTTP 상태 코드(있는 경우), 재시도 횟수, 시나리오 ID를 기록하며 API 키와 요청 전문은 기록하지 않는다.
